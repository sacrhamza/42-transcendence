The registration endpoint **`POST /api/auth/register`** has been created in the NestJS backend.

It currently validates the request body, including the username, email, and password. Malformed JSON and input that fails the configured validation rules are rejected.

**Status: integration pending.** Registration is not ready for end-to-end use yet. We are waiting for the user-creation endpoint from the FastAPI service, `database-apis`.

**Request flow**

1. The frontend sends a registration request to NestJS.
2. NestJS validates the input and hashes the password.
3. NestJS calls FastAPI through an internal HTTP request.
4. FastAPI stores the user in the database.
5. NestJS returns the result to the frontend.

NestJS acts as a **server for the frontend** and a **client of FastAPI**.

**Coordination needed with the FastAPI team**

Before completing integration, we need to agree on the internal API contract: endpoint paths, request fields, HTTP status codes, and response bodies.

Please share the FastAPI OpenAPI documentation (`/docs` or `/openapi.json`, if enabled), or request/response examples covering these cases:

| Operation or situation | Information to confirm |
|---|---|
| Find user by email or username | Endpoint, query parameters, and returned user fields |
| User not found | Does the API return `404`, or `200` with `null`? |
| Create user successfully | Success status and response body |
| Duplicate email or username | Confirm `409 Conflict` and the error body |
| Invalid internal payload | Validation status and error format |
| Missing or invalid internal API key | Status code returned |
| Database unavailable or internal failure | Status code and safe error format |

We also need to confirm that the creation endpoint accepts a **password hash generated by NestJS**, whether that field is called `password` or `passwordHash`, and that it does not hash it again.

**One current integration issue:** our NestJS HTTP client throws an exception when FastAPI returns `404`. During registration, however, “user not found” is an expected lookup result that allows registration to continue. We need the agreed response format so that `UsersService` can translate this specific result into `null`, while still propagating timeouts and service failures.

FastAPI does not send Python exceptions directly to NestJS. It sends **HTTP statuses and response bodies**, which NestJS translates into appropriate public responses.

Database uniqueness must also be enforced for email and username. Preliminary lookups alone cannot prevent two simultaneous requests from creating duplicates.

**How to call the endpoint**

Method: `POST`  
URL: `http://localhost:3000/api/auth/register`  
Header: `Content-Type: application/json`

Request body:

```json
{
  "username": "aadouay",
  "email": "ayoub@example.com",
  "password": "V7!qR2#zL9@m"
}
```

Test with curl:

```bash
curl -i -X POST http://localhost:3000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{
    "username": "aadouay",
    "email": "ayoub@example.com",
    "password": "V7!qR2#zL9@m"
  }'
```

Use HTTPS in the deployed application; NestJS handles password hashing. The frontend does not need the internal API key used between NestJS and FastAPI. Passwords and password hashes must never appear in public responses.

Invalid input returns **`400 Bad Request`** with validation messages. The successful registration response and duplicate email/username behavior will be documented once the FastAPI contract and integration are finalized.

For now, input validation can be tested, but a valid request is not guaranteed to create an account.
